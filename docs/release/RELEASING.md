# 版本发布与回退

## 版本与来源

- 当前正式版本 `1.0.0`，正式源码标签 `v1.0.0`；审核来源与内容清单见同目录版本记录。
- `main` 可以继续开发；标签、正式Release及内容清单共同保存已发布版本，不移动已有标签。
- 游戏、包名、更新日志和发布记录保持同一版本。存档schema独立维护，不能为了修改展示版本而重置存档。
- 官方审核通过不表示笔记已发布或全机型已测；审核、挂载、设备验证分别记录。

## 后续版本步骤

1. 在 `codex/` 功能分支完成改动和相称验证。整理CHANGELOG Unreleased并评估存档兼容。
2. 更新 `package.json` 与锁文件版本，以及确实存在的界面版本标识。修复用补丁号，新功能用次版本，不兼容升级用主版本。
3. 完成调试后运行 `npm test`、`npm run package`。不要在验收时混用开发构建与正式构建。
4. 审计 `dist/` 和游戏 ZIP；平台规则变化时按上传页当前口令加载官方Skill。记录实际平台模拟器、Android/iOS扫码与华为鸿蒙设备验证结果，未测的明确保留。
5. 验证完成、准备冻结时生成 `docs/release/v版本-manifest.json`，列出四个运行资源的字节数和SHA-256，记录审核来源；再运行 `node scripts/verify-package.mjs`。旧清单保留，不为让验证通过而改写旧版本内容。
6. 新建该版本发布记录，包含变更、测试、兼容性、存档影响与已知问题。将文档/脚本提交到 `main`，完成构建与附件校验，再创建指向该提交的带说明Git标签。
7. 推送提交和标签，创建**现有仓库**中的Release（当前公开，不为发布而擅自更改可见性），附游戏ZIP、文档ZIP、推广ZIP、独立图标及SHA256SUMS。源码由该标签归档；不把构建目录或ZIP堆进源码历史。
8. 上传后核对Release标签、附件名/大小/散列、仓库可见性。平台提交和审核通过后登记实际状态；需要推广时另行发布笔记。

## 构建与散列

`scripts/package.mjs` 从 `package.json` 读取版本，自动生成正式包名和历史兼容别名；文档包包含维护指南，推广素材单独归档。`scripts/verify-package.mjs` 要求当前版本存在内容清单，核对文件内容，防止正式版本被悄悄改动。

GitHub Release 的 ZIP 整体散列以随附 `SHA256SUMS.txt` 为准。ZIP重新构建可能因封装时间变化导致整体散列不同；`v版本-manifest.json` 比较解压后的四个运行资源，用于确认游戏内容是否相同。发布附件不得被不同内容覆盖；修复发布新版本。

1.0.0审核包的HTML/CSS使用CRLF，Git源码使用LF。构建脚本显式统一这两份交付文本为CRLF，避免新克隆或跨系统构建仅因换行不同而改变冻结内容；源码换行不影响游戏逻辑。

## 回退

优先取旧标签对应的Release附件，比对随附SHA256SUMS，再按平台允许的更新/回退流程处理。不要直接重置远端 `main` 或改指旧标签。源码层面可新建修复分支并回退对应变更，通过新提交和补丁版本发布。

旧代码未必兼容新存档。回退前核实存档schema和迁移方向，不自动清空玩家数据。仓库Release归档与小红书线上版本是两个状态：改变Git标签或下载包不会自动改变平台运行版本。
